# Database Schema

The schema is defined by `ShowroomBillingDbContext.OnModelCreating` and the entity classes under `src/ShowroomBilling.Infrastructure/Persistence/`, and created by the migrations in `Persistence/Migrations/`. This page lists the tables and the rules that the model does not make obvious. The application uses PostgreSQL 18. For provisioning and backups, see [11_deployment_and_ops.md](./11_deployment_and_ops.md#4-postgresql-deployment).

**Names.** Tables are snake_case (`bill_revisions`). Columns carry the C# property names and must be double-quoted in SQL: `SELECT "InvoiceNumber", "CreatedAtUtc" FROM public.bills`. The one exception is `database_identity`, whose columns are `key`, `value` and `updated_at_utc`. Indexes and constraints have EF's names (`IX_bills_CreateOperationId`, `CK_bills_state`). EF records the applied migrations in `"__EFMigrationsHistory"`.

Design principles:

- PostgreSQL is the system of record
- a bill revision is not changed after it is saved; an edit appends a new one
- the database owns numbering state
- no local durable business storage
- new non-deterministic persisted IDs are UUIDv7 values generated by the .NET application for better B-tree insertion locality; existing UUIDv4 values and deterministic identity GUIDs remain valid

## 1. Tables

### 1.1 `bills`

One row per bill.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `CurrentRevisionId` | uuid, nullable | The bill's current `bill_revisions` row |
| `State` | text | See [03_bill_state_machine.md](03_bill_state_machine.md) |
| `InvoiceNumber` | text, nullable | Assigned when the bill is created (`CreateDraftAsync`), not at push |
| `FiscalYear` | text, nullable | Indian fiscal year of the number (`YYYY-YY`) |
| `InvoiceCore` | bigint, nullable | The integer behind `InvoiceNumber`. Numbering reads this, never the display text. Null only for a legacy custom number, which holds no place in the sequence |
| `SupersededByBillId` | uuid, nullable | Set on the old bill by revise |
| `CreateOperationId` | uuid, nullable | Client id of the Save that created the bill; a repeated Save resolves to this row |
| `EditedAfterPush` | boolean | True while Tally holds a voucher that an edit or renumber has made stale; the next push alters it. Cleared by a successful alter, Mark as Pushed and Mark as Pending |
| `CreatedAtUtc`, `UpdatedAtUtc` | timestamptz | |
| `xmin` | system column | Row version. Every tracked save checks it, so a writer that read the bill before another change committed gets 409 "Concurrent change" |

Constraints and indexes:

- check `"State" IN ('draft','pending','posting','posted','failed','reconciliation_required','revised','voided')`
- unique `("FiscalYear", "InvoiceNumber")` where the number is not null: the duplicate-number guard
- unique `("CreateOperationId")` where it is not null
- unique `("FiscalYear", "InvoiceCore")` where the core is not null: two bills of a year cannot hold the same core, whatever their numbers' text says (the text depends on the prefix, suffix and padding in Settings). It also serves the numbering skip window

The `UniqueInvoiceCore` migration (14 November 2026) made that index unique, and `DropShowroomAndDocumentType` (15 November 2026) builds both again without the showroom (§1.10). On a database that already holds two bills of one year on one core or one number, neither fails: the index is left a plain one and a PostgreSQL `WARNING` says how many values are repeated. Find them with

```sql
SELECT "FiscalYear", "InvoiceCore", count(*), array_agg("InvoiceNumber")
FROM public.bills
WHERE "InvoiceCore" IS NOT NULL
GROUP BY "FiscalYear", "InvoiceCore"
HAVING count(*) > 1;
```

and, once each pair has been dealt with in the app (Change Bill Number, or Delete Local), make the index unique by hand as the role that owns the tables:

```sql
DROP INDEX IF EXISTS public."IX_bills_FiscalYear_InvoiceCore";
CREATE UNIQUE INDEX "IX_bills_FiscalYear_InvoiceCore"
    ON public.bills ("FiscalYear", "InvoiceCore") WHERE "InvoiceCore" IS NOT NULL;
```

(The number's index is `IX_bills_FiscalYear_InvoiceNumber`, on `("FiscalYear", "InvoiceNumber") WHERE "InvoiceNumber" IS NOT NULL`.)

Other indexes:

- `("State", "CreatedAtUtc", "Id")` and `("CreatedAtUtc")` for the Bills list
- GIN trigram index on `"InvoiceNumber"` for the Bills tab's contains search

### 1.2 `bill_revisions`

Saved versions of a bill's contents. A row is written once and not changed.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `BillId` | uuid FK → `bills."Id"`, `ON DELETE CASCADE` | |
| `RevisionNo` | integer | Counts up within the bill |
| `SnapshotJson` | jsonb | Full bill payload |
| `PartyName`, `BillDate`, `GrandTotal` | text, date, numeric(18,3) | Copies for search and lists |
| `SupersedesRevisionId` | uuid, nullable | The revision this one replaced |
| `CreatedAtUtc` | timestamptz | |

Constraints and indexes: unique `("BillId", "RevisionNo")`; checks `"RevisionNo" > 0` and `"GrandTotal" >= 0`; `("BillId", "CreatedAtUtc")`; `("BillDate", "Id")`; GIN trigram index on `"PartyName"`.

### 1.3 `invoice_sequences`

Numbering state, one row per fiscal year.

| Column | Type | Notes |
|---|---|---|
| `FiscalYear` | text PK | `YYYY-YY` |
| `NextValue` | bigint | Where the next allocation starts; check `> 0` |
| `MinNextValue` | bigint | One past the highest core kept for Tally: raised when a bill whose voucher Tally holds is deleted or renumbered. Roll-back stops at it, and a reservation passes over the core just under it ([docs/04 §2.7](04_numbering_and_idempotency.md)) |
| `UpdatedAtUtc` | timestamptz | |

The row is locked with `SELECT ... FOR UPDATE` during allocation and rollback. Behaviour is in [04_numbering_and_idempotency.md](04_numbering_and_idempotency.md).

### 1.4 `invoice_number_reservations` (dropped)

Dropped on 11 October 2026; see §1.10. Builds up to 10 October 2026 wrote one row per bill created (`"IdempotencyKey"` = `draft:{billId}`). A bill's number is on its own row, and a repeated Save is recognised by `bills."CreateOperationId"`.

### 1.5 `audit_events`

General audit/event trail.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `EntityType` | text | `bill`, `numbering`, `masters`, `settings`, `print_asset`, `admin` |
| `EntityId` | text | For a bill, its id |
| `EventType` | text | For bills, the names in `Contracts.Bills.BillAuditEvents` |
| `ActorType` | text | `device`, `admin`, `system`, or `api` (master refresh) |
| `ActorId` | text, nullable | `desktop` for device requests; the admin's label or session id for admin requests |
| `PayloadJson` | jsonb | |
| `CreatedAtUtc` | timestamptz | |

Indexes: `("EntityType", "EntityId", "CreatedAtUtc")`, `("EntityType", "EntityId", "EventType", "CreatedAtUtc")`, `("EventType", "CreatedAtUtc")`.

Audit rows are append-only. They are never cascade-deleted with bills and are not purged during edit-and-repush. Hard deletion appends `bill.deleted`, leaving the complete history queryable by the deleted bill ID.

Posting outcomes live here and nowhere else: `tally.posted`, `tally.failed` and `tally.outcome.unknown`. The posting status that retry and repost return (`LastErrorCode`, `LastErrorMessage`, `LastRemoteId`) is rebuilt from the latest of these. A `tally.posted` row carries `tallyAction` (`Create` or `Alter`), `tallyMasterId`, which is what an edited bill's next push alters, `company`, and `updatedExistingVoucher`, true when a create's `REMOTEID` was already in Tally and Tally updated that voucher instead of making one. After it, a `tally.voucher.filed` row records what reading the voucher back found: `tallyMasterId`, `voucherNumberInTally`, `voucherDateInTally`, `totalInTally`, `invoiceNumber`, `numberDiffers` (the number Tally filed it under is not the bill's, or there is none) and `pushAuditId`, the `tally.posted` row it belongs to. A `bill.push.requested` row records the attempt's `tallyAction` and, for an Alter, `targetTagValue`, the voucher it names.

Rows that older builds wrote and current code does not: `numbering.sales_invoice.reserved` (one per number issued) and entity type `draft_lease`. They stay.

### 1.6 Tally master lists

`tally_masters` holds the four lists last read from Tally, one row per list:

| Column | Type | Notes |
|---|---|---|
| `MasterType` | text PK | `companies`, `ledgers`, `stock_items`, `voucher_types` |
| `FetchedAtUtc` | timestamptz | When the list was read from Tally |
| `ItemCount` | integer | How many entries the list holds, so the freshness report need not read the lists |
| `ItemsJson` | jsonb | The whole list, in name order: `[{ "name": … }]`, with `isActive` for a company and `baseUnit`, `hsnCode` for a stock item |

A refresh replaces the row (an upsert) and writes a `masters.<type>.ingested` audit row in the same transaction. A read returns the whole list. Nothing looks inside a list, so there are no item rows and no index beside the key.

Until 14 November 2026 this was five tables: `tally_master_snapshot_batches` and a row table per master. The `MasterSnapshotsInOneTable` migration carries each master's current list across and drops them (§1.10).

### 1.7 `cloud_settings` and `database_identity`

`cloud_settings` is the one row of shared settings: Tally connection, numbering, print, and ledger mapping columns, plus three jsonb columns and one text column of JSON. `ItemMasterDataJson` and `KaratMappingDataJson` hold the Masters lists. `PrintLayoutJson` (default `{}`) holds margins, logo/signature placements, optional watermark placement, density/border/pin settings and the ordered section rows; asset IDs in it refer to `print_assets."Id"`, and legacy JSON without `watermark`/`pageLayout` is read with structured defaults. `BankChargesLedger` (varchar 256, default `''`, added by `AddBankChargesLedger` on 27 November 2026) is the ledger bills' bank charges are credited to; unlike the other ledger columns it may stay empty, since only a bill with bank charges needs it. What the fields are is in [08_settings_catalog.md](08_settings_catalog.md).

The row is made by the first request that reads the settings. It is stored under a fixed `Id` (`CloudSettingsEntity.FirstSettingsId`) with `INSERT … ON CONFLICT DO NOTHING`, so of several requests that find no settings at the same moment the primary key lets one add the row; the others wait for it and read it. The same statement writes the row's `settings.seeded` audit event, so there is one of those too. Until 21 November 2026 each of them added a row with an id of its own, so a database first used by an older build can hold more than one. Every read and write takes one row: the newest by `"UpdatedAtUtc"` and, where two carry the same time, the higher `"Id"` (`CloudSettingsRow.InUse`). A save moves that row's time on, so an extra row is never read and never changes; no migration removes it. To see whether a database has one, and to remove it as the owner role:

```sql
-- The first line is the row in use. One line is right.
SELECT "Id", "UpdatedAtUtc", "ActiveCompanyName", "InvoicePrefix"
  FROM public.cloud_settings ORDER BY "UpdatedAtUtc" DESC, "Id" DESC;

DELETE FROM public.cloud_settings
 WHERE "Id" <> (SELECT "Id" FROM public.cloud_settings ORDER BY "UpdatedAtUtc" DESC, "Id" DESC LIMIT 1);
```

`BatchHoursJson` (`text`, not null, default `{}`; added on 21 November 2026 by the `AddBatchHours` migration) holds the shop hours a batch of the Batch Data Scheduler keeps to, as JSON: `Opens`, `Closes` (times of day in India), `ClosedOn` (the weekly closed day, 0 = Sunday) and `GapMinutes` ([17_synthetic_batch.md](17_synthetic_batch.md#shop-hours)). `{}`, an empty value, or one that cannot be read means no hours are set. The default is the database's as well as the application's, so a server build from before the column, which does not name it, still writes a valid row.

`database_identity` is a key/value table (`key`, `value`, `updated_at_utc`). The row `environment` says `DEV` or `PROD`; see [DEV_SETUP.md](../DEV_SETUP.md#database).

### 1.8 `admin_passcodes` and `admin_sessions`

`admin_passcodes` has one row. A first passcode is stored under a fixed `Id` (`AdminPasscodeEntity.FirstPasscodeId`), so the primary key refuses a second; a passcode set by a build before 15 November 2026 has an id of its own and is changed in place. Its columns: `PasscodeSalt` (base64, 16 bytes), `PasscodeHash` (base64, 32-byte PBKDF2-SHA256), `Iterations` (120 000), `CreatedAtUtc`, `UpdatedAtUtc`. Configured via `POST /api/admin/passcode`; verified via `POST /api/admin/unlock`.

`admin_sessions` has one row per admin unlock. The token is returned once at unlock time; the table stores only its SHA-256 hash.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `TokenHash` | text | Unique index |
| `ActorLabel` | text | Who unlocked; becomes the `ActorId` of that session's audit rows |
| `IssuedAtUtc` | timestamptz | |
| `ExpiresAtUtc` | timestamptz | 30 minutes after issue; check `"ExpiresAtUtc" > "IssuedAtUtc"` |
| `RevokedAtUtc`, `RevokedReason` | timestamptz, text; nullable | Set by `/api/admin/logout` |

Index: `("ExpiresAtUtc")`.

### 1.9 `print_assets`

Logo, signature, and watermark images uploaded by the operator, stored inline.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `AssetKind` | text | check `IN ('logo','signature','watermark')` |
| `FileName` | text | |
| `ContentType` | text | e.g. `image/png` |
| `Bytes` | bytea | raw bytes |
| `ByteLength` | bigint | check `> 0` |
| `CreatedAtUtc` | timestamptz | |

Index: `("AssetKind")`. Upload validation accepts only PNG/JPEG content whose file signature matches, with a 2 MiB decoded-byte cap.

### 1.10 Columns and tables removed since October 2026

The `DropUnusedColumnsAndIndexes` migration removed six columns nothing read: `bills."CreatedBy"`, `bill_revisions."TotalsJson"` and `"RawJson"` on the four master snapshot tables. It also removed twelve indexes that were a prefix of another index or sat on a single-row table.

Before dropping a column the migration copies its values into a table named `dropped_20261010_<table>_<column>` (`Id` plus the value, only rows that held something), in the same transaction. Rolling the migration back restores the columns from those tables. They are not part of the EF model. When the release has settled, remove them by hand:

```sql
DROP TABLE IF EXISTS
    public.dropped_20261010_bills_created_by,
    public.dropped_20261010_bill_revisions_totals_json,
    public.dropped_20261010_tally_company_snapshots_raw_json,
    public.dropped_20261010_tally_ledger_snapshots_raw_json,
    public.dropped_20261010_tally_stock_item_snapshots_raw_json,
    public.dropped_20261010_tally_voucher_type_snapshots_raw_json;
```

The `DropDraftEditLeases` migration dropped the `draft_edit_leases` table the same day. Nothing ever wrote it: no build of the Desktop took a lease. If the table holds any row it is first copied to `dropped_20261010_draft_edit_leases` in the same transaction, and rolling back recreates the table, its three indexes and those rows. An empty table, the expected case, leaves no copy. When the release has settled:

```sql
DROP TABLE IF EXISTS public.dropped_20261010_draft_edit_leases;
```

The `DropInvoiceNumberReservations` migration (11 October 2026) dropped `invoice_number_reservations` (§1.4). Its rows are first copied to `dropped_20261011_invoice_number_reservations` in the same transaction, and rolling back recreates the table, its two indexes and those rows. Production held a row for every bill created before 11 October, so the copy exists there. When the release has settled:

```sql
DROP TABLE IF EXISTS public.dropped_20261011_invoice_number_reservations;
```

The `DropUnreadColumns` migration (14 November 2026) removed eleven columns that were written and never read: `bills."CounterId"` (always null), `"BillType"` (always `sales`) and `"VoidedAtUtc"`; `bill_revisions."SubmittedAtUtc"` and `"FinalizedAtUtc"`; `"Parent"`, `"PrimaryGroup"`, `"IsRevenue"` and `"Gstin"` on `tally_ledger_snapshots`; `"ParentType"` and `"IsDeemedPositive"` on `tally_voucher_type_snapshots`. When a bill was voided or pushed is in its audit rows (`bill.voided`, `tally.posted`).

Here the copy is one table per source table, `dropped_20261114_<table>`, holding `Id` and that table's dropped columns for the rows where one of them held something (a per-column name for the longest pair would not fit PostgreSQL's 63 characters). Rolling back restores the columns and their values. When the release has settled:

```sql
DROP TABLE IF EXISTS
    public.dropped_20261114_bills,
    public.dropped_20261114_bill_revisions,
    public.dropped_20261114_tally_ledger_snapshots,
    public.dropped_20261114_tally_voucher_type_snapshots;
```

The `MasterSnapshotsInOneTable` migration (14 November 2026) replaced the five master snapshot tables with `tally_masters` (§1.6). Each master's current list is written into the new table, and every one of the five old tables that held rows is first copied whole to `dropped_20261114_<table>_rows`, in the same transaction. Rolling back recreates the old tables with their indexes and puts those rows back; on a database that was created on the new table it rebuilds the rows from the lists. When the release has settled:

```sql
DROP TABLE IF EXISTS
    public.dropped_20261114_tally_company_snapshots_rows,
    public.dropped_20261114_tally_ledger_snapshots_rows,
    public.dropped_20261114_tally_stock_item_snapshots_rows,
    public.dropped_20261114_tally_voucher_type_snapshots_rows,
    public.dropped_20261114_tally_master_snapshot_batches_rows;
```

The `DropShowroomAndDocumentType` migration (15 November 2026) removed `"ShowroomId"` from `bills`, `invoice_sequences`, `admin_passcodes`, `admin_sessions` and `print_assets`, and `"DocumentType"` from `invoice_sequences`. The application runs for one showroom and numbers one kind of document, so every row held the same two values (the showroom id `9b961fc2-035f-3dd3-43e0-4f8f136e7682`, which admin audit rows still carry as their `EntityId`, and `sales_invoice`). The key of `invoice_sequences` became the fiscal year, and the indexes that began with the showroom were built again without it.

The copy is one table per source table, `dropped_20261115_<table>`. For the four tables with an `Id` it holds `Id` and `ShowroomId` of the rows that held another showroom's id; the application never wrote one, so the copies are empty, and a row that did hold one is from then on a row like any other (the migration raises a `WARNING` with the count). `dropped_20261115_invoice_sequences` holds the whole table as it was if any of its rows held another showroom or document type; the rows of one fiscal year then become one row, standing where the furthest of them stood. Rolling back restores the columns, their values, the key and the indexes. When the release has settled:

```sql
DROP TABLE IF EXISTS
    public.dropped_20261115_bills,
    public.dropped_20261115_admin_passcodes,
    public.dropped_20261115_admin_sessions,
    public.dropped_20261115_print_assets,
    public.dropped_20261115_invoice_sequences;
```

`RetireDraftBillState` converts legacy draft bills to pending and tightens the state constraint. If it finds any drafts, it records their IDs, current revision IDs and update times in `public.dropped_20261128_bills_draft`. Rolling back restores the draft state for bills that are still pending with the same revision and update time. The table can be removed after the rollback window closes.

These side tables are removed by hand and not by a migration on purpose: a migration that deleted them would also delete the copies a restored older database makes on its way up.

## 2. Rules

### 2.1 Relations and deletes

- `bills."CurrentRevisionId"` names a `bill_revisions` row; `bill_revisions."BillId"` → `bills."Id"` with `ON DELETE CASCADE`
- `print_assets` rows are referenced from `cloud_settings."PrintLayoutJson"`
- deleting a bill (admin only) removes its revisions, clears `"SupersededByBillId"` on bills that pointed at it, and keeps its audit rows

### 2.2 Uniqueness

- one revision number per bill
- one invoice number, and one number core, per fiscal year (two partial unique indexes on `bills`)
- one bill per `"CreateOperationId"`
- one numbering row per fiscal year
- one admin passcode

### 2.3 Concurrency

- there are no edit locks: opening a bill does not reserve it
- two counters saving the same bill are caught by the bill's row version (409 "Concurrent change")
- a push claims the bill with a conditional update to `posting`. If the API crashes mid-call, `StuckPostingRecoveryHostedService` moves any bill stranded in `posting` to `reconciliation_required` with a `bill.posting.recovered` audit event

### 2.4 Retention

Each successful admin unlock deletes the `admin_sessions` rows that expired more than 30 days ago. Nothing else is deleted on a schedule: bills, revisions, numbering rows, print assets, settings and audit history stay until an admin deletes a bill.
