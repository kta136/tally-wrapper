# Database Schema

The schema is defined by `ShowroomBillingDbContext.OnModelCreating` and the entity classes under `src/ShowroomBilling.Infrastructure/Persistence/`, and created by the migrations in `Persistence/Migrations/`. This page lists the tables and the rules that the model does not make obvious. Production runs PostgreSQL 18, self-hosted on an Oracle Cloud Infrastructure VPS; deployment and operational responsibilities are documented in [11_deployment_and_ops.md](./11_deployment_and_ops.md#4-postgresql-deployment).

**Names.** Tables are snake_case (`bill_revisions`). Columns carry the C# property names and must be double-quoted in SQL: `SELECT "InvoiceNumber", "CreatedAtUtc" FROM public.bills`. The one exception is `database_identity`, whose columns are `key`, `value` and `updated_at_utc`. Indexes and constraints have EF's names (`IX_bills_CreateOperationId`, `CK_bills_state`). EF records the applied migrations in `"__EFMigrationsHistory"`.

Design principles:

- PostgreSQL is the system of record
- a bill revision is not changed after it is saved; an edit appends a new one
- the database owns numbering state
- no local durable business storage
- new non-deterministic persisted IDs are UUIDv7 values generated by the .NET application for better B-tree insertion locality; existing UUIDv4 values and deterministic identity GUIDs remain valid

## 1. Tables

### 1.1 `bills`

One row per bill.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `ShowroomId` | uuid | Always the default showroom |
| `CounterId` | uuid, nullable | Originating counter, when the client sends one |
| `BillType` | text | `sales` |
| `CurrentRevisionId` | uuid, nullable | The bill's current `bill_revisions` row |
| `State` | text | See [03_bill_state_machine.md](03_bill_state_machine.md) |
| `InvoiceNumber` | text, nullable | Assigned when the bill is created (`CreateDraftAsync`), not at push |
| `FiscalYear` | text, nullable | Indian fiscal year of the number (`YYYY-YY`) |
| `InvoiceCore` | bigint, nullable | The integer behind `InvoiceNumber`. Numbering reads this, never the display text. Null only for legacy custom numbers |
| `SupersededByBillId` | uuid, nullable | Set on the old bill by revise |
| `CreateOperationId` | uuid, nullable | Client id of the Save that created the bill; a repeated Save resolves to this row |
| `EditedAfterPush` | boolean | True while Tally holds a voucher that an edit or renumber has made stale; the next push alters it. Cleared by a successful alter, Mark as Pushed and Mark as Pending |
| `CreatedAtUtc`, `UpdatedAtUtc` | timestamptz | |
| `VoidedAtUtc` | timestamptz, nullable | |
| `xmin` | system column | Row version. Every tracked save checks it, so a writer that read the bill before another change committed gets 409 "Concurrent change" |

Constraints and indexes:

- check `"State" IN ('draft','pending','posting','posted','failed','reconciliation_required','revised','voided')`
- unique `("ShowroomId", "FiscalYear", "InvoiceNumber")` where the number is not null: the duplicate-number guard
- unique `("CreateOperationId")` where it is not null
- `("ShowroomId", "FiscalYear", "InvoiceCore")` for the numbering skip window
- `("ShowroomId", "State", "CreatedAtUtc", "Id")` and `("ShowroomId", "CreatedAtUtc")` for the Bills list
- GIN trigram index on `"InvoiceNumber"` for the Bills tab's contains search

### 1.2 `bill_revisions`

Saved versions of a bill's contents. A row is written once; only its two push timestamps are set later.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `BillId` | uuid FK → `bills."Id"`, `ON DELETE CASCADE` | |
| `RevisionNo` | integer | Counts up within the bill |
| `SnapshotJson` | jsonb | Full bill payload |
| `PartyName`, `BillDate`, `GrandTotal` | text, date, numeric(18,3) | Copies for search and lists |
| `SupersedesRevisionId` | uuid, nullable | The revision this one replaced |
| `CreatedAtUtc` | timestamptz | |
| `SubmittedAtUtc` | timestamptz, nullable | First push of this revision |
| `FinalizedAtUtc` | timestamptz, nullable | Latest push of this revision |

Constraints and indexes: unique `("BillId", "RevisionNo")`; checks `"RevisionNo" > 0` and `"GrandTotal" >= 0`; `("BillId", "CreatedAtUtc")`; `("BillDate", "Id")`; GIN trigram index on `"PartyName"`.

### 1.3 `invoice_sequences`

Numbering state, one row per `("ShowroomId", "FiscalYear", "DocumentType")` (the primary key). `DocumentType` is `sales_invoice`; `FiscalYear` is `YYYY-YY`.

| Column | Type | Notes |
|---|---|---|
| `NextValue` | bigint | Where the next allocation starts; check `> 0` |
| `MinNextValue` | bigint | Floor for rollback. Raised past the core of a deleted or renumbered bill whose voucher Tally holds |
| `UpdatedAtUtc` | timestamptz | |

The row is locked with `SELECT ... FOR UPDATE` during allocation and rollback. Behaviour is in [04_numbering_and_idempotency.md](04_numbering_and_idempotency.md).

### 1.4 `invoice_number_reservations` (unused)

Not written and not read. Older builds wrote one row per bill created (`"IdempotencyKey"` = `draft:{billId}`). The table, its EF mapping and those rows stay until a migration drops it. A bill's number is on its own row, and a repeated Save is recognised by `bills."CreateOperationId"`.

### 1.5 `audit_events`

General audit/event trail.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `EntityType` | text | `bill`, `numbering`, `masters`, `settings`, `print_asset`, `admin` |
| `EntityId` | text | For a bill, its id |
| `EventType` | text | For bills, the names in `Contracts.Bills.BillAuditEvents` |
| `ActorType` | text | `device`, `admin`, `system`, or `api` (master refresh) |
| `ActorId` | text, nullable | `desktop` for device requests; the admin's label or session id for admin requests |
| `PayloadJson` | jsonb | |
| `CreatedAtUtc` | timestamptz | |

Indexes: `("EntityType", "EntityId", "CreatedAtUtc")`, `("EntityType", "EntityId", "EventType", "CreatedAtUtc")`, `("EventType", "CreatedAtUtc")`.

Audit rows are append-only. They are never cascade-deleted with bills and are not purged during edit-and-repush. Hard deletion appends `bill.deleted`, leaving the complete history queryable by the deleted bill ID.

Posting outcomes live here and nowhere else: `tally.posted`, `tally.failed` and `tally.outcome.unknown`. The posting status that retry and repost return (`LastErrorCode`, `LastErrorMessage`, `LastRemoteId`) is rebuilt from the latest of these. A `tally.posted` row carries `tallyAction` (`Create` or `Alter`) and `tallyMasterId`, which is what an edited bill's next push alters.

Rows that older builds wrote and current code does not: `numbering.sales_invoice.reserved` (one per number issued) and entity type `draft_lease`. They stay.

### 1.6 Tally master snapshots

`tally_master_snapshot_batches` is the header of one pull of one master type:

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `ShowroomId` | uuid | |
| `MasterType` | text | `companies`, `ledgers`, `stock_items`, `voucher_types` |
| `FetchedAtUtc` | timestamptz | |
| `Status` | text | check `IN ('active', 'superseded')`; new batches are `active` |
| `ItemCount` | integer | Row count at ingestion time |

Indexes: `("ShowroomId", "MasterType", "FetchedAtUtc")`, `("ShowroomId", "MasterType", "Status")`.

The rows are in four tables, each with `Id`, `BatchId` (FK → the batch, `ON DELETE CASCADE`), `ShowroomId`, `Name` and one index, `("BatchId", "Name")`:

- `tally_company_snapshots` — `IsActive`
- `tally_ledger_snapshots` — `Parent`, `PrimaryGroup`, `IsRevenue`, `Gstin`
- `tally_stock_item_snapshots` — `Alias`, `BaseUnit`, `HsnCode`, `Karat`
- `tally_voucher_type_snapshots` — `ParentType`, `IsDeemedPositive`

A refresh inserts the new batch and deletes every earlier batch of that master type in the same transaction; their rows go by cascade. Nothing is written as `superseded`. A `superseded` batch left by an older build is deleted by the next refresh of its master type.

### 1.7 `cloud_settings` and `database_identity`

`cloud_settings` is the one row of shared settings: Tally connection, numbering, print, and ledger mapping columns, plus three jsonb columns. `ItemMasterDataJson` and `KaratMappingDataJson` hold the Masters lists. `PrintLayoutJson` (default `{}`) holds margins, logo/signature placements, optional watermark placement, density/border/pin settings and the ordered section rows; asset IDs in it refer to `print_assets."Id"`, and legacy JSON without `watermark`/`pageLayout` is read with structured defaults. What the fields are is in [08_settings_catalog.md](08_settings_catalog.md).

`database_identity` is a key/value table (`key`, `value`, `updated_at_utc`). The row `environment` says `DEV` or `PROD`; see [DEV_SETUP.md](../DEV_SETUP.md#database).

### 1.8 `admin_passcodes` and `admin_sessions`

`admin_passcodes` has one row per showroom (unique `"ShowroomId"`): `PasscodeSalt` (base64, 16 bytes), `PasscodeHash` (base64, 32-byte PBKDF2-SHA256), `Iterations` (120 000), `CreatedAtUtc`, `UpdatedAtUtc`. Configured via `POST /api/admin/passcode`; verified via `POST /api/admin/unlock`.

`admin_sessions` has one row per admin unlock. The token is returned once at unlock time; the table stores only its SHA-256 hash.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `ShowroomId` | uuid | |
| `TokenHash` | text | Unique index |
| `ActorLabel` | text | Who unlocked; becomes the `ActorId` of that session's audit rows |
| `IssuedAtUtc` | timestamptz | |
| `ExpiresAtUtc` | timestamptz | 30 minutes after issue; check `"ExpiresAtUtc" > "IssuedAtUtc"` |
| `RevokedAtUtc`, `RevokedReason` | timestamptz, text; nullable | Set by `/api/admin/logout` |

Index: `("ShowroomId", "ExpiresAtUtc")`.

### 1.9 `print_assets`

Logo, signature, and watermark images uploaded by the operator, stored inline.

| Column | Type | Notes |
|---|---|---|
| `Id` | uuid PK | |
| `ShowroomId` | uuid | |
| `AssetKind` | text | check `IN ('logo','signature','watermark')` |
| `FileName` | text | |
| `ContentType` | text | e.g. `image/png` |
| `Bytes` | bytea | raw bytes |
| `ByteLength` | bigint | check `> 0` |
| `CreatedAtUtc` | timestamptz | |

Index: `("ShowroomId", "AssetKind")`. Upload validation accepts only PNG/JPEG content whose file signature matches, with a 2 MiB decoded-byte cap.

### 1.10 Columns and tables removed on 10 October 2026

The `DropUnusedColumnsAndIndexes` migration removed six columns nothing read: `bills."CreatedBy"`, `bill_revisions."TotalsJson"` and `"RawJson"` on the four master snapshot tables. It also removed twelve indexes that were a prefix of another index or sat on a single-row table.

Before dropping a column the migration copies its values into a table named `dropped_20261010_<table>_<column>` (`Id` plus the value, only rows that held something), in the same transaction. Rolling the migration back restores the columns from those tables. They are not part of the EF model. When the release has settled, remove them by hand:

```sql
DROP TABLE IF EXISTS
    public.dropped_20261010_bills_created_by,
    public.dropped_20261010_bill_revisions_totals_json,
    public.dropped_20261010_tally_company_snapshots_raw_json,
    public.dropped_20261010_tally_ledger_snapshots_raw_json,
    public.dropped_20261010_tally_stock_item_snapshots_raw_json,
    public.dropped_20261010_tally_voucher_type_snapshots_raw_json;
```

The `DropDraftEditLeases` migration dropped the `draft_edit_leases` table the same day. Nothing ever wrote it: no build of the Desktop took a lease. If the table holds any row it is first copied to `dropped_20261010_draft_edit_leases` in the same transaction, and rolling back recreates the table, its three indexes and those rows. An empty table, the expected case, leaves no copy. When the release has settled:

```sql
DROP TABLE IF EXISTS public.dropped_20261010_draft_edit_leases;
```

## 2. Rules

### 2.1 Relations and deletes

- `bills."CurrentRevisionId"` names a `bill_revisions` row; `bill_revisions."BillId"` → `bills."Id"` with `ON DELETE CASCADE`
- `tally_*_snapshots."BatchId"` → `tally_master_snapshot_batches."Id"` with `ON DELETE CASCADE`
- `print_assets` rows are referenced from `cloud_settings."PrintLayoutJson"`
- deleting a bill (admin only) removes its revisions, clears `"SupersededByBillId"` on bills that pointed at it, and keeps its audit rows

### 2.2 Uniqueness

- one revision number per bill
- one invoice number per `("ShowroomId", "FiscalYear")` (partial unique index on `bills`)
- one bill per `"CreateOperationId"`
- one numbering row per `("ShowroomId", "FiscalYear", "DocumentType")`

### 2.3 Concurrency

- there are no edit locks: opening a bill does not reserve it
- two counters saving the same bill are caught by the bill's row version (409 "Concurrent change")
- a push claims the bill with a conditional update to `posting`. If the API crashes mid-call, `StuckPostingRecoveryHostedService` moves any bill stranded in `posting` to `reconciliation_required` with a `bill.posting.recovered` audit event

### 2.4 Retention

Each successful admin unlock deletes the `admin_sessions` rows that expired more than 30 days ago. Nothing else is deleted on a schedule: bills, revisions, numbering rows, print assets, settings and audit history stay until an admin deletes a bill.
