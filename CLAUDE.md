# CLAUDE.md

Notes for Claude (or any AI coding agent) working in this repo. Read [README.md](README.md) and [DEV_SETUP.md](DEV_SETUP.md) first — those describe the system; this file describes how to *work* on it.

## What this repo is

Windows desktop billing app for a jewellery showroom. Each counter runs the Desktop (WPF, `net10.0-windows`), a client of one ASP.NET Core API (`net10.0`) that runs as a Windows service on the Tally server. That API owns the PostgreSQL 18 database and dials TallyPrime's local XML endpoint. The Desktop never starts or contains an API.

- **Solution:** `ShowroomBilling.sln` · target framework is **`.NET 10`** across every project (Desktop is `net10.0-windows`).
- **Hosts:** `src/ShowroomBilling.Api`, `src/ShowroomBilling.Desktop`, and `src/ShowroomBilling.ServerTray` (WinForms installer and tray that installs the API as a Windows service on the Tally server and holds its database connection). A Desktop's only connection setting is the server address (`DesktopBootstrap:ApiBaseUrl`, edited in Settings → Server).
- **Layers:** `Contracts` (DTOs, shared between hosts), `Application`, `Infrastructure` (EF Core + Tally XML), `Printing` (QuestPDF templates). (There is no `Domain` project — business rules live in `Application` / `Infrastructure`.) `Application` declares an interface only where something stands in for the implementation: a test double (`ITallyPoster`, `ICloudSettingsService`) or a second implementation. A service nothing substitutes (`BillService`, `NumberingService`, `AdminAuthService`, `PrintAssetService`) is used as its Infrastructure class, by controllers too; do not add an interface for it.
- **Tests:** `tests/ShowroomBilling.Tests` (API + infra) and `tests/ShowroomBilling.Desktop.Tests` (view models, the views themselves, and everything of the server tray).

## Workflow rules

- **Smoke-test after every slice for WPF work.** `dotnet build` validates XAML compiles — it does not validate binding paths, layout, visibility triggers, or keyboard flow. Launch the exe and exercise the changed feature before claiming done.
- **Launch it with `tools/run-scratch.ps1`, not `dotnet run` or F5, on any PC that also runs the real app.** The script gives the dev build a throwaway PostgreSQL 18 container, empty settings folders, a stand-in Tally on port 9000 and its own API on port 5108, so it cannot reach the saved production server or post test vouchers to TallyPrime. (A dev Desktop started any other way reads this PC's saved server address and would work against production.) See [DEV_SETUP.md](DEV_SETUP.md#run-against-a-scratch-database). A build fails while that app is running (file lock); close it first, or build `-c Release` for the tests.
- **`ViewSmokeTests` is the automated half of that.** It loads every view against the real `MainWindowViewModel` (no window is shown) and fails on a XAML load error or a binding path error, so run the Desktop tests after any XAML change. It cannot see focus or keyboard flow; those still need the exe. A new view is picked up automatically; give it a data context in `DataContextFor` if `MainWindow.xaml` gives it one.
- **To look at the views without launching the app, run it in snapshot mode.** Set `TALLYWRAPPER_VIEW_SNAPSHOTS` to a folder and run `ViewSmokeTests`: each view (and each Settings section) is saved there as a PNG, laid out at 1280×800 with the test's sample data. Use it after any change to `Styles.xaml`, `DesignTokens.xaml` or a view. Hover, press and disabled states of the button styles are covered by `ButtonStyleTests` instead, since a snapshot cannot show them.
- **To look at a printed bill after a layout change,** set `TALLYWRAPPER_PRINT_SAMPLES` to a folder and run `BillDocumentRenderTests`: it keeps `sample_invoice.pdf` and `sample_invoice_overflow.pdf` there. `PrintDispatcherTests` with the same variable keeps what a direct print sends to the printer (`direct_print.xps` and a picture of each page).
- **Update docs in the same pass as code.** If a slice changes a setting, endpoint, shortcut, or user-visible flow, edit `docs/` and `DEV_SETUP.md` alongside the code. Don't leave them drifted.
- **Scope discipline.** For refactors or UI audits, prefer the smallest visual/logical change that closes the gap. No pre-emptive abstractions, no unrelated cleanup, no renaming "while you're in there".
- **Ask before rebuilding at scale.** If a request could mean "touch a handful of files" or "rewrite every view", use `AskUserQuestion` before starting. The blast radius matters.
- **Never `--no-verify` or skip pre-commit hooks.** If a hook fails, fix the cause; don't bypass.

## EF migrations

Pass the connection string explicitly when migrating any remote database. The EF tools silently ignore `ASPNETCORE_ENVIRONMENT` and fall back to the localhost default in `appsettings.json`, which either fails loudly or quietly migrates a local database you did not mean to touch:

```powershell
dotnet ef database update --project src/ShowroomBilling.Infrastructure --startup-project src/ShowroomBilling.Api --connection "<postgres-connection-string>"
```

- **Production never migrates itself.** Migrations are applied by hand, as the role that owns the tables, before a new build is started. The server service tries at start-up, but its database role may not alter the schema (SQLSTATE `42501`), and nothing else applies them. A new build on a database without its migrations cannot read or save a bill; this took production down on 10 October 2026, when it showed only as an empty Bills tab. It is now reported: `DatabaseHealth` holds the pending-migration count, `/api/health` returns it as `database.pendingMigrationCount`, the Desktop shows `DB BEHIND` with a banner, and the tray says "upgrade needed". Keep that signal working when you touch health or start-up code; `SchemaBehindPostgresTests` replays the outage. Never tell anyone a deployed build will migrate production by itself. The steps are in [docs/11 §11](docs/11_deployment_and_ops.md).
- **A migration that drops data copies it aside first**, because whoever applies it may skip the backup. Follow `20261010124946_DropUnusedColumnsAndIndexes` (`20261011114506_DropInvoiceNumberReservations` is the whole-table version): copy the values into a `dropped_<date>_<table>_<column>` table in the same transaction (or one `dropped_<date>_<table>` table for several columns of a table, as `20261114114013_DropUnreadColumns` does; a name must fit PostgreSQL's 63 characters), make `Down` restore from it, and write every statement conditionally (`IF EXISTS` / `IF NOT EXISTS`), because a migration that fails at start-up leaves the API in limited mode. Add a test that runs it both ways against real rows, like `DropUnusedColumnsMigrationPostgresTests`. The side tables are removed later by hand ([docs/10 §1.10](docs/10_database_schema.md)), never by a migration: that would also delete the copies a restored older database makes on its way up. **Dropping also makes the release all-at-once:** an older build still maps the column or table, so it fails against the migrated database. Say so in docs/11 §11 when you add one.
- **On a machine that also runs the real app, point the EF tools away from its settings first**, or the design-time host reads the saved production connection: set `SHOWROOM_BILLING_APPDATA` to an empty folder and `SHOWROOM_BILLING_POSTGRES` to a dummy value. `migrations add` does not connect to a database.
- Keep deployment-specific hosts, credentials, role names and secret paths in the private site runbook. The public [operations guide](docs/11_deployment_and_ops.md#4-postgresql-deployment) describes how to configure the API.

## Tally integration

- An operator action sends at most one voucher write. Read-only queries can retry. An ambiguous write outcome requires admin reconciliation after checking Tally. See the [integration contract](docs/05_tally_integration_contract.md) and [bill state machine](docs/03_bill_state_machine.md).
- Resolve an Alter target before claiming the bill. Match the company, type, current Tally date and master ID. For a fallback lookup by number, verify the single candidate against the recorded date and total. Refuse an unsafe match.
- Commit the conditional `posting` claim before the remote write. After acceptance, read back the filed voucher number for the audit. Report differences to the operator. Changing a Tally voucher type’s numbering settings can renumber existing vouchers.
- The [Tally XML reference](docs/06_tally_xml_golden_path.md) records the proven request shapes, result classification and conditions for live revalidation.

## API errors

- **Every error body is RFC 7807 ProblemDetails**, written by `DomainExceptionHandler` (`src/ShowroomBilling.Api/Middleware/`). Its mapping table is the code plus the theory in `DomainExceptionHandlerTests`; a new domain exception gets a line in both. Desktop API clients read `detail` / `title` for non-2xx responses.
- **Throw `RequestValidationException` (Application) for a user-facing input error**, with a message written for the operator and no parameter name. A plain `ArgumentException` that names a parameter gets ` (Parameter 'x')` appended by .NET; the handler strips it, but new code should not rely on that.
- **No per-action `try/catch` around domain exceptions in controllers.** Let them bubble. The only legitimate controller-level error return is result-is-null `NotFound()` for read endpoints.
- **Do not check a `[FromBody]` request for null.** With `[ApiController]` a missing body for a non-nullable parameter is answered with a 400 before the action runs (`MissingBodyContractTests` pins this). Where a body really is optional (push, retry, void, revise, delete, master refresh), the parameter is nullable and the action substitutes a default request.

## Admin and device auth

Endpoints and the throttling numbers: [docs/09](docs/09_api_spec.md).

- **Unlock.** Press `~` (backtick) anywhere outside a text box, with no dialog open, to open `AdminUnlockDialog`. `?` and the backtick are run by `MainWindow.OnKeyDown` through `Shell/BareKeyShortcuts`, which takes the key only when its gated `*KeyCommand` ran, so in a text box the character is typed and an awaited prompt is never replaced. Do not make them `KeyBinding`s again: a key binding marks its key handled even while its command cannot execute, and for months neither character could be typed anywhere. `Ctrl+Alt+G` (the Batch data scheduler, V1's hidden key, brought back on 20 November 2026) goes the same way: it acts only while admin is unlocked and no dialog is open, and otherwise does nothing. It is left out of the shortcuts list on purpose. The token lives in `AdminTokenStore` (30 min TTL) and rides as `X-Admin-Token`. If an admin call is made while locked, the unlock dialog opens and the call goes ahead once it closes unlocked.
- **First passcode.** `AdminUnlockDialog` runs `LoadStatusCommand` on open and shows either the unlock form or a "Set passcode" form (`ShowUnlockForm` / `ShowInitialSetupForm` on `AdminUnlockViewModel`). It is the only in-app place to set the first passcode, because Settings → Admin appears only once unlocked; the server accepts a first passcode only from a Desktop on the server PC itself (loopback). Minimum length is `Contracts.Settings.SettingLimits.MinAdminPasscodeLength`, which both the server and the view model read.
- **Server side.** `AdminAuthenticationHandler` (scheme `AdminToken`) validates the token and endpoints are gated with `[Authorize(Policy = AdminPolicy.PolicyName)]`; downstream code reads the session from the `ClaimsPrincipal`. Unlock and passcode rotation go through `AdminUnlockThrottle`, which is in-memory and resets on API restart by design.
- **Which policy a new endpoint gets.** A mutating endpoint gets `[Authorize(Policy = DevicePolicy.PolicyName)]`: on a server install that means a caller inside the trusted LAN range; for an API on a developer's own machine it means the `X-Device-Token` file secret, which `DeviceTokenHandler` attaches only when the Desktop's API address is loopback. An admin-only endpoint gets the admin policy **only**; do not stack both. Reads are unauthenticated.
- **An action that needs admin only for some bills** keeps the device policy. Saving an edit to a `posted` bill is the case: `BillsController.UpdateDraft` passes on whether the request carries an admin session, and the workflow throws `AdminSessionRequiredException` (403) when it is needed and missing.

### Hide admin-only controls while locked

A button that will fail auth gives the operator no feedback, so admin-only controls are hidden until unlock.

- `BillsViewModel.IsAdminUnlocked` (raised on `AdminTokenStore.Changed`) hides Delete Selected, Change Bill Number and the admin-only context menu items (Change Bill Number, Mark as Pushed, Mark as Pending, Delete Local).
- Settings → Admin is added to and removed from the sidebar by `SettingsSectionCoordinator.SyncAdminSection`; the Batch Data Scheduler group binds `AdminVm.IsUnlocked`.
- **Edit is the exception**, because it needs admin only for a posted bill. It stays visible; on a posted row it asks for unlock before the bill opens (`BillsViewModel.EditRowAsync`), and the Invoice tab asks again at Save if the session has expired since.
- **A secret follows the same rule.** The Desktop holds one, the bill hand-over key (Settings → Hand-over, DPAPI-protected in `%LOCALAPPDATA%`), and never shows it: the section draws dots and offers only Change… and Remove. The database connection lives on the server and is edited from its tray. If a secret is ever shown, fill it in only while admin is unlocked, clear it on lock, and never replace text the operator is typing.
- **Context menus are popups, a separate visual tree**, so `RelativeSource AncestorType=UserControl` from a `<MenuItem>` finds nothing. The Bills row `Border` sets `Tag="{Binding DataContext, RelativeSource={RelativeSource AncestorType=UserControl}}"` to hand `BillsViewModel` down, and menu items bind `{Binding PlacementTarget.Tag.IsAdminUnlocked, RelativeSource={RelativeSource AncestorType=ContextMenu}}`. Every item on that menu binds its command this way, including Open Details and Print, whose commands the shell hands to `BillsViewModel` (`OpenDetailsCommand`, `PrintSelectedCommand`); do not add `Click` handlers. `ViewSmokeTests` connects each context menu to its owner and fails on an item whose command binding found nothing.
- The "Admin unlocked" pill in [TopBarView.xaml](src/ShowroomBilling.Desktop/Views/TopBarView.xaml) shows only while unlocked and invokes `LockCommand` on click.

## Bill payload validation

`BillValidator.Validate` (Application) runs on every client-supplied `BillPayloadDto` before it is stored: create, update, and revise when it carries a payload. The rules are listed in [docs/09 §2.2.1](docs/09_api_spec.md). **Do not validate `Subtotal == Σ LineTotal`** or `LineTotal == Rate × Quantity`; jewellery pricing makes both invalid assumptions. Add new invariants to `BillValidator.Validate`, not controllers or services.

## Start-up hosted services

Bound hosted-service work and log failures so the API can start and continue serving. `StuckPostingRecoveryHostedService` waits for database initialization, retries its sweep every five minutes after an unavailable database, and pauses while migrations are pending. A conditional sweep recovers claims older than ten minutes.

The Desktop and tray share `GET /api/health`. Tally-company health has its own request and timeout. `DatabaseHealth` bounds the database check at two seconds, shares the result for five seconds and logs changes in reachability. On a routine poll the Desktop changes the Database indicator at the first failure and pauses billing after the second. Startup and explicit refresh act immediately. See the [health endpoints](docs/09_api_spec.md).

## Bill hand-over

How it works: [docs/18](docs/18_bill_handover.md).

- **A handed-over bill is an ordinary bill.** It is created and updated through the same calls as the Invoice tab, with the hand-over's save ID as `ClientOperationId`. Do not add a column, flag, note, audit event or payload field that marks it, and nothing may count handed-over bills.
- **The line mapping goes through the Invoice tab's own classes** (`BillLineViewModel`, `BillCalculator`, `InvoicePayloadMapper`, `InvoiceEditMapper`). A change to how the Invoice tab prices or saves a line changes the hand-over too; `HandoverBillMapperTests` checks that each line keeps its total, reopens to it, never has an input below zero, and is what the Invoice tab would save.
- **Only the published app registers the `tallywrapper:` scheme** (Release, Production, no `SHOWROOM_BILLING_*APPDATA` override, single-file exe; `HandoverUrlScheme.ShouldRegister`). Keep that guard, or a test or a scratch run takes the links from the real app on the counter. A test that needs the registry writes under a scratch key, never `HKCU\Software\Classes`.

## Audit rows

- **Append-only.** Bill audit rows are never purged during edit-and-repush and are not cascade-deleted with the bill. `BillAuditStore.GetAuditAsync` reads by entity ID even after the bill row is gone, so the `bill.deleted` tombstone and the full prior history stay queryable.
- **Actors** come from `IAuditActorContext`: device-authenticated mutations record `device/desktop`, admin mutations record `admin/<actor>`, and start-up or background work records `system`.
- **Never build audit JSON by string concatenation**; an invoice number or reason containing a quote used to break it silently. Bill events go through `BillAuditStore.Write(billId, eventType, state, at, details)` and every other row through `AuditRow.Create` (Infrastructure/Persistence); both serialize an object. The wire shape is `{ "state": "...", "details": { ... } }` and the Desktop's `BillDetailsViewModel` reads `details.reason` / `details.invoiceNumber` / `details.fiscalYear`; keep that.
- Bill event names are the constants in `Contracts.Bills.BillAuditEvents`; when you add one, add its title to the Desktop's `BillAuditTrailMapper.TitleFor` (a test fails otherwise).

## Transactions

Most commands are a single `SaveChangesAsync`, which EF wraps in an implicit transaction. A few open an explicit one because they make several round trips on the same `ShowroomBillingDbContext`: creating a bill (`BillLifecycleWorkflow.CreateNewDraftAsync`) and revising one (number, bill, revision and audit commit together), `BillAdminWorkflow.DeleteAsync`, and `ChangeInvoiceNumberAsync` (the save plus the sequence reclaim).

`NumberingService.ReserveAsync` needs the caller's transaction (it throws without one) and leaves the save to the caller, so the number and the bill commit in one batched round trip. **A caller that opens a transaction around `ReserveAsync` must call `SaveChangesAsync` afterwards.** The push is the deliberate exception; see Tally integration above.

## Shared constants and helpers you must use

- **Bill states:** [`ShowroomBilling.Contracts.Bills.BillStates`](src/ShowroomBilling.Contracts/Bills/BillStates.cs) is canonical, including `ReconciliationRequired`. **Do not compare `bill.State` to string literals.**
- **Invoice number formatting:** [`ShowroomBilling.Contracts.Numbering.InvoiceNumberFormatter`](src/ShowroomBilling.Contracts/Numbering/InvoiceNumberFormatter.cs) is the single formatter, used by server-side reservation, change-number auto-format and the Desktop `ChangeNumberDialog` preview. If you need to render or compare an invoice number, go through it; never hand-build `{prefix}{year}/{NNNN}{suffix}`.
- **The settings row:** a query of `cloud_settings` takes its row through `CloudSettingsRow.InUse()` (Infrastructure/Settings), never with an ordering of its own. A database first used by a build from before 21 November 2026 can hold a second row, and every read and write must name the same one. The first row is added by `CloudSettingsRow.AddFirstAsync` under the fixed id `CloudSettingsEntity.FirstSettingsId` (`INSERT … ON CONFLICT DO NOTHING`, with its `settings.seeded` event in the same statement), which is what keeps requests arriving together on a new database to one row; do not `Add` a settings entity. `CloudSettingsSeedingPostgresTests` holds both.
- **File locations:** [`ShowroomBilling.Contracts.AppPaths`](src/ShowroomBilling.Contracts/AppPaths.cs) is the only place that knows `%APPDATA%\ShowroomBilling` (`DataDirectory`, `LogsDirectory`) and `%LOCALAPPDATA%\ShowroomBilling` (`LocalDirectory`: device token). Build every path from it; do not call `Environment.GetFolderPath` for an app file. Both test projects redirect it to a scratch folder in a module initializer (`TestSupport/TestAppData.cs`), so a store that bypasses `AppPaths` would make the tests read or overwrite the real settings of whoever runs them, including the saved database connection. `TestIsolationTests` / `AppPathsTests` check the redirect.

## Numbering

How reservation, forward-skip and roll-back behave: [docs/04 §2.4–2.7](docs/04_numbering_and_idempotency.md).

- **Every path that sets `InvoiceNumber` (create, revise, change-number) must also set `InvoiceCore`.** Occupancy is read from the stored core, never from display text, because a suffix such as `-A2` parses as core 2. A row with a NULL core is a legacy custom number with no digits to it and occupies no core; nothing parses display text any more. The index on the core is unique (`UniqueInvoiceCore`), and change-number holds the year's sequence row while it checks for a clash.
- **A path that removes a bill from the sequence's trailing slot, or moves it, calls `NumberingSequenceReclaimer.ReclaimAsync` inside its transaction**, as delete and change-number do. Do not re-invent the roll-back: it also raises `MinNextValue` past a core whose voucher Tally still holds. No roll-back goes below that floor, and `NumberingService` passes over the core just under it, which matters when that core is ahead of the sequence. Nothing reconciles a sequence at start-up.
- **Change-number accepts digits only** and formats them with `InvoiceNumberFormatter`.
- A repeated Save is recognised by `bills.CreateOperationId`. There is no reservation table: a bill's own row holds its number.
- **One showroom, one kind of numbered document.** No table carries a showroom id or a document type (both were dropped on 15 November 2026 by `DropShowroomAndDocumentType`): a sequence is a row per fiscal year, and there is one admin passcode row, kept one by its fixed id (`AdminPasscodeEntity.FirstPasscodeId`). Do not add a scoping column "for later"; every query, key and index had to carry the last one.

## Master data refresh

- **One `Refresh from Tally` button per master section**, not a Fetch and a Refresh. It re-pulls from Tally and reloads the dropdown, and Settings loads any empty snapshot when it opens. Don't reintroduce a separate "Fetch" button; operators forgot the second click.
- Each button names the masters it wants (`SettingsMasterSnapshotWorkflow.RefreshAsync`): the Ledgers button sends `ledgers` and then `voucher-types`. A request with no master type refreshes all four, which is what System Health's "Refresh all" is for.
- **`POST /api/masters/refresh` returns one `TallyMasterRefreshResult` per master fetched.** Don't deserialize it as a single accept-shape record; that once swallowed real failures. `SettingsRefreshSummaryFormatter.Summarize` renders per-master counts, or the first failing master.
- **`TallyMasterRefresher.RefreshAllAsync` runs the four masters sequentially**, each in its own DI scope. Tally's local XML endpoint times out under concurrent reads.
- **Each list is one row of `tally_masters`**, the whole list as JSON in the shape of its item record (`Contracts/Masters/MasterSnapshotItems.cs`); a refresh replaces the row. Do not bring back a row per ledger: nothing looks inside a list. A property renamed on an item record no longer matches the stored lists until they are refreshed from Tally, and a new one stays empty until then.

## Tests

Where the test database server comes from: [DEV_SETUP.md](DEV_SETUP.md#database-tests).

- **Every test that touches the database runs on PostgreSQL 18**, the production version. There is no in-memory provider and no code path that exists only for tests.
- **Derive from `DatabaseTest`** to get a fresh copy of the migrated template for each test; `CreateDbContext()` returns a new context on it. A test that needs something else (a database stopped at an older migration, several connections racing) takes `PostgresFixture` in its constructor and asks it directly, as the classes under `Postgres/` do.
- **A test class that needs the database carries `[Trait("Category", "Postgres")]`**: inherited from `DatabaseTest`, set on the class everywhere else. CI runs `Category!=Postgres` on Windows and `Category=Postgres` on Linux, so a class without the trait fails the Windows job, and these tests must stay free of Windows-only assumptions (path separators, DPAPI).
- **Check what was stored with a second context.** `ExecuteUpdateAsync` / `ExecuteDeleteAsync` change rows without touching entities a context already tracks, so reading back through the service's context can show the old values.
- **A Desktop view model always has its API clients**: they are required constructor parameters and nothing checks them for null. A test that is not about the server passes `FakeBillsApi`, `FakeNumberingApi.Offline()` or the `OfflineApi` fakes (`OfflineApi.Settings()` for a whole settings view model), whose calls fail as an unreachable server's do. `DesignSample` gives its fakes the sample's own bills and settings, because switching tab loads them again; a sample that stops matching its server shows up as changed pictures in snapshot mode.
- **A new or changed endpoint gets a contract test** in `tests/ShowroomBilling.Tests/Contracts/`. `TestApiFactory` boots the real API in-process on a database of its own, with auto-migrate off and `StubTallyMasterRefresher`; the device token comes from `factory.GetDeviceToken()`. `MasterRefreshContractTests` is the example.

## Things I learned the hard way

- Translate boolean status into a labelled indicator that an operator can interpret.
- **A unit is kept as it was saved, and a row's Unit drop-down offers that row's own unit.** A line's unit is printed (`22.800g`) and sent to Tally (`22.345 g`, `6550/g`) exactly as stored, so never rewrite "g" to "gm" to tidy it: Tally knows the stock item by its own unit. Item lists saved by older builds write grams as "g", and a drop-down whose list does not hold the bound value shows nothing (it does not change the value): every such line on the Invoice tab had an empty Unit cell, and so had the item in Settings → Masters. `BillLineViewModel.UnitChoices` and `ItemMasterRowVm.UnitChoices` are "gm", "ct" and the row's own unit; they only grow, because a list that loses the selected entry is the combo-box trap described under the item and karat cells. `UnitChoicesTests` and `InvoiceCatalogViewTests` hold it.
- **A bill reads the saved items and karats from `MasterCatalog`, never the rows Settings is editing.** `SettingsViewModel.Catalog` is published when settings are loaded or saved, and only if the items or karats are not what they were; its entries are the `ItemMasterEntry` / `KaratMasterEntry` records, which never change. `InvoiceViewModel.ItemMasters` / `KaratMasters`, a hand-over and the batch scheduler's karat list read it. `ItemMasterRowVm` / `KaratMasterRowVm` belong to Settings → Masters alone; do not hand one to anything outside it, or a half-typed wastage prices a bill. When a new catalogue arrives under an open bill, `InvoiceViewModel.OnCatalogPublished` swaps the lists and then points each line at the new entry of the same name with `BillLineViewModel.RebindMasters`, which applies no defaults. That method is the point: a line that lost its item would pick it up again by name at its next change and put the item's default wastage and labour over what had been typed. (The cells were combo boxes when this was written, which drop a selection that has left their list; the `SuggestBox` does not, but the line must still be moved to the new entry.) `SettingsReloadTests` holds this and `InvoiceCatalogViewTests` holds it on the real screen; `SettingsReloadTests` also holds that showing the Settings tab does not reload while an edit is open (`RefreshOnShownAsync`).
- **The Invoice form is emptied when the bill is saved, not when it has printed** (`ShellPrintCoordinator.HandleInvoiceSaveCompletedAsync`). The print is made from the saved bill, post-save prints run one after another, and nothing the print does afterwards may touch the form: the operator is already typing the next bill.
- Preserve the SVG text and transparency fallback in `PrintDispatcher`. Inspect `PrintDispatcherTests` output after a font or drawing change. For raster pages use `BitmapImage` for XPS serialization. Let the XPS writer escape `Glyphs.UnicodeString`. See the [printing specification](docs/07_printing_spec.md).
- The Batch Data Scheduler’s amount, item, weight, date and shop-hours limits are product rules. Changes require product sign-off. Preserve pre-run confirmation and the saved count on partial completion. See the [batch specification](docs/17_synthetic_batch.md).
- **A view model's commands are `[RelayCommand]` methods, and what a property change refreshes is said on the property.** `[RelayCommand(CanExecute = nameof(CanX))]` on `X` / `XAsync` gives `XCommand`; `[NotifyCanExecuteChangedFor]` and `[NotifyPropertyChangedFor]` on the `[ObservableProperty]` field replace an `OnXxxChanged` hook that only raised other things. Keep a hook for work (recompute, save a preference), and keep a manual raise where the cause is not one of this class's own properties (a collection changing, another view model's event). The exception is `BillsViewModel`: its commands that run a `BillActions` method are built in the constructor (`RowCommand`, `ContextRowsCommand`, `SelectionCommand`, which say which rows the action takes), because a wrapper method and a can-execute member for each would be more code. For those hand-built ones the old trap still holds: setting an `[ObservableProperty]` in the constructor runs its hook, and a hook that touches a command not yet assigned throws, so assign them first. A generated command is created on first use and has no such order.
- **`RelativeSource AncestorType=UserControl` resolves to the nearest UserControl *and reads its current DataContext*** — not the inherited one. If the UserControl has `DataContext="{Binding Foo}"` set on it in the host (e.g. `SettingsView DataContext="{Binding Settings}"` in MainWindow), then `AncestorType=UserControl` hits `SettingsViewModel`, not `MainWindowViewModel`. Silent bugs (missing command on wrong VM) result. Reach for `AncestorType=Window` when you need `MainWindowViewModel` from inside a nested view. Precedent: the `OpenSyntheticBatchCommand` button was silently inert for months because of this.
- **A money box bound with `UpdateSourceTrigger=PropertyChanged` and a `StringFormat` or converter drops the decimal point while it is typed.** WPF writes the text again from the amount after every key, so "100." becomes "100" and the next keys land after it: a discount typed as 100.5 took ₹1,005 off a bill (found 27 November 2026, there since the redesign). Bind an amount with the default lost-focus update and `MoneyTextConverter` (paise kept, an empty box is none), as the Discount and Bank charges boxes are; Ctrl+S, F9 and New bill flush the focused box first (`InvoiceView.CommitFocusedEdit`). `InvoiceAmountBoxViewTests` types into the boxes a key at a time; a view-model test cannot see this.
- **`KeyBinding Key="P"` without a modifier fires even while a TextBox has focus** (plain-letter keys aren't marked Handled by TextBox for routing purposes). Filter/search inputs can trigger parent commands mid-typing. Always pair bare-letter shortcuts with `Ctrl`/`Shift`/`Alt`, or skip the keybinding and rely on a button.
- **Reading `dotnet-trace` for an `async void` entry point is a trap.** `App.OnStartup` shows up with multi-second *inclusive* time in the trace, but that includes the entire async continuation that runs on the dispatcher message-loop *after* `window.Show()` has returned (via `MainWindow.OnLoaded` → `InitializeAsync`). The actual pre-window-paint cost is much smaller — verify with the `[startup-timing]` log line that `App.OnStartup` emits (Information level, written to `%APPDATA%\ShowroomBilling\logs\desktop-*.log`), not by reading inclusive ms off the speedscope flame graph. Phases logged: `hostBuild`, `hostStart`, `resolveWindow`, `showWindow`, `windowVisibleAt` (total).
- Bound a database health probe with `Task.WaitAsync` and start the attempt on `Task.Run`. A silent pooled connection can block before the first await, and Npgsql cancellation can outlive the caller’s deadline. `DatabaseHealthPostgresTests` covers this using a relay and a short keepalive interval.
- **An animation that never stops keeps WPF drawing every frame, seen or not.** The Settings preview's progress bar was indeterminate for good inside a collapsed box, and its marquee kept the app at about a third of a core while it sat idle on any tab (found 26 November 2026, there since the October redesign). The bar's template now runs the marquee only while the bar is visible (`ProgressBarMarqueeTests`), and a bar's `IsIndeterminate` is bound to the work it shows. A new `Storyboard` with `RepeatBehavior="Forever"` gets the same `IsVisible` condition. `LazyViewHost` builds a view when it is first shown, and it looks again at `DataBind` priority before it does: at the window's first layout no host's `Visibility` binding has a value yet, so every host reads as visible, and until 26 November 2026 every tab and dialog was built at start-up (the window showed about 0.7 s later for it). A dialog is therefore built the first time it opens; `FocusOnShown` and the dialogs' own `IsVisibleChanged` handlers still run then (`LazyViewHostTests`).
- **`PublishReadyToRun=true` is set in one place**, `Get-PublishArguments` in `tools/PublishCommon.ps1`, which every publish script uses; change it there if you need a non-R2R build (for example to reproduce a JIT-only bug). It costs about 10 % binary size and 30 s of publish time for roughly 800 ms off a cold launch. The same file's `Remove-PublishFolder` is how a publish script empties an output or staging folder, and it refuses anything outside the repo's `publish\` directory; the scripts' other deletes are of single items inside the folder they have just published to.
